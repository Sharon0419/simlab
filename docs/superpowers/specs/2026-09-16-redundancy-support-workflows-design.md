# 装备 n 中取 k 与保障多工序开发设计

日期：2026-09-16。适用项目：C:/Users/sharo/Documents/ChatGPT/Simlox。
基线：v0.11.0，当前分支 codex/m3-supply-maintenance。
状态：业务选择已逐项确认；本文的实施方案及默认细节待整体评审，尚未编码。

## 1. 目标与范围

本轮两个 P0：装备 n 中取 k；保障活动可配置多工序、紧前与紧后。
装备结构保持 System→LRU→SRU，不扩展其他装备能力，不增加混编。
供应中断、横向调拨、有限运输容量及报废后处置不在本轮。

## 2. 已确认的装备规则

- 两层均支持：System 下 LRU 组、LRU 下 SRU 组。
- 同一直接上级下同型号组成一组，不跨型号合组。
- 所有正常工作部件参与运行，累计工作时长并承受故障风险；不增加备用与切换机制。
- 当前任务中，剩余可用数达到 k 则继续，正常结束后维修；低于 k 则中止并返航。
- 即使仍达到 k 也尽早维修，不等降到阈值以下。
- 返回并进入维修等待后，等待人员或备件期间同样不能执行新任务。
- 维修作业期间装备不能执行新任务；修复完成且保障资源释放后恢复任务资格。

## 3. 装备实现方案与默认细节

采用独立扩展配置，关联现有父项与子项型号。n 来自现有结构数量，只录入最低可用数 k，避免数量存在两套来源。

- 校验 k 为整数且 1≤k≤n，父子关系必须实际存在；同一父子关系不允许重复配置。
- 未配置时默认 k=n，保持原串联语义。
- 每个组分别满足阈值，上级的所有组均满足才具有工作能力；不引入组间替代。
- 从 SRU 向 LRU 再向装备递归计算工作能力，不再因任一 SRU 故障就直接判整台装备不可用。
- 区分实物自身损坏、下级组不满足阈值、装备任务资格。可继续当前任务不等于可以带着待修工单再次出动。
- 一个 LRU 内部未达停机阈值的 SRU 故障也必须登记待修需求，不因上级仍可用漏修。
- 零时长及同一时刻的故障、修复和出动先统一结算，再做任务资格判断，避免依赖事件插入顺序。
- 原有预防维修、报废与终身小时计数口径保留；寿命到限完成当前飞行的既有规则不被误改为故障返航规则。
- 运行暴露采用工作能力递归判断：仍可工作的 LRU 中正常 SRU 全部运行；已经失去工作能力的 LRU 内部不再累计运行暴露。返航阶段按现有运行时段规则处理仍在工作的部件。
- 待修父件换下后，装备装入合格替换件并完成机上保障即可恢复，仍不等待拆下件修复返库。

以上新增默认细节属于本文实施建议，不冒充用户逐项选择。

## 4. 已确认的保障规则

适用于修复性维修、预防性维修（原位、换件、拆下件），以及出动准备、日历检查和飞行小时检查。

- 支持自定义工序，分别设置名称、时长、人员与设备需求。
- 只采用完成后开始依赖：全部紧前工序完成，后续工序才可开工。
- 支持并行分支及汇合；不增加同时开始、同时结束或依赖间隔类型。
- 每道工序的全部资源到齐后开始，完成立即释放；不在活动开始时占用整个活动的资源总和。
- 已开始工序跨班继续至完成，持续占用资源；后续工序仍须满足开工班次条件。
- 同一装备不同保障活动串行，单项活动内部可并行。
- 自定义工序不能绕过拆卸、安装等必要业务动作及其先后约束。

## 5. 工序执行与配置设计

推荐一套公共工序执行器，维修、准备和检查通过各自业务适配接入。公共部分只处理依赖、资源、班次和记录；拆装实物流转、年龄更新、维修计次仍由现有业务模块负责。

备选方案是分别给各活动增加一套执行逻辑，初期改动较局部，但依赖校验、班次和资源处理容易分叉；不采用。另一个选择是通用流程编排平台，能支持条件、循环及复杂依赖，但超出已确认范围，也不采用。

### 5.1 配置与动作

- 活动绑定工序方案，方案内维护工序标识、名称、时长定义、资源需求、紧前工序；紧后关系从紧前配置自动推导，避免两边分别维护产生冲突。
- 保留现有固定/随机时长支持范围，不在本轮增加新的分布类型。
- 普通自定义工序只产生耗时与资源占用；必要动作工序带明确业务类型，如拆卸、安装、实际修复、最终检测。
- 换件方案中拆卸必须先于安装，安装必须先于机上最终检测；缺件时安装等待合格备件，不提前占住安装所需人员与设备。
- 拆下件维修仍有独立工单与流程，可与原装备完成换装后的任务并行；同机活动串行不把脱离装备的维修锁在原装备上。
- 实际修复引起的年龄更新和维修计次只执行一次，自定义清洁、搬运、辅助检测不增加修复次数。
- 工序间不循环、不返工、不做概率分支；原位/换件的既有比例先选择路径，再执行该路径方案。
- 活动全部必需工序完成才结束，结束时释放活动互斥权；装备恢复还需满足其他待修和检查约束。
- 保留已有活动优先级，活动一旦启动不被后到活动抢占。就绪工序使用稳定顺序提交现有共享资源队列，保证固定种子可复现。
- 仿真截止时保留未完成工序和等待状态，不将其伪造为完成。

### 5.2 输入校验

运行前阻止：不存在的紧前工序、自依赖、循环依赖、重复标识、负时长、非法资源数量、错误活动绑定、缺失必要动作、必要动作顺序错误。

错误明确定位到方案、工序和字段。资源暂时忙或当前不在班次是正常等待；永久无法满足的配置应在可判断时提前报错。

### 5.3 界面与结果

- 装备结构附近配置最低可用数 k，并显示已有数量 n。
- 保障配置提供方案、工序及依赖编辑，紧后关系可查看，不要求重复录入。
- 首版以表格编辑为主，不增加拖拽流程设计器；保留必要校验提示，长说明按需查看。
- 结果新增工序明细：活动、工序、装备/实物、地点、就绪/开工/结束时刻、状态、资源与等待时长。
- 等待紧前、等待班次、等待资源分别记录；总活动历时按开始结束计算，不能把并行工序时长相加冒充活动历时。
- 结果及全部轮次导出覆盖新增记录；装备故障事件可追溯组内可用数和 k。

## 6. 兼容与实施边界

- 旧项目无新配置时保留原路径和随机抽样顺序，既有结果可读取，不自动改写用户项目库。
- 旧单作业准备/检查与预定义维修仍可使用；配置新工序方案后由新执行器接管该活动，避免新旧流程重复执行。
- 增加扩展版本与读写校验，旧软件对无法支持的新项目明确报错；不改动原厂字典含义。
- n 中取 k 对当前支持且存在相应部件模型的执行路径提供一致语义；不允许配置保存成功却在运行时静默忽略。详细执行路径映射在实施计划中列出并验证。

## 7. 验收标准

装备：两层 3取2、2取1；恰好k和k−1；多个型号组串联；同型号不同父实例独立；任务继续/返航；待修禁出动；修复恢复；同刻事件；k=n旧串联；预防与报废交互。

工序：单链、并行、汇合；独立资源与共享资源竞争；跨班；零时长；循环与错误动作拒绝；同机活动互斥；拆下件与原装备解耦；缺件等待；截止未完成记录；六类活动接入。

综合：两层冗余装备执行任务后，落地触发多工序维修；校验库存与实物守恒、资源不超用、寿命及维修计次不重复、结果明细与汇总一致。

交付：相关回归与完整现有测试、源码桌面检查、打包与安装检查、新示例项目及导出、旧案例兼容核对、版本说明及 Git 同步。测试和安装完成前不得声称软件已交付。

## 8. 开发安排

建议先完成 n 中取 k 状态模型，再完成公共工序执行与各活动接入，最后联调界面、结果和案例。这是依赖驱动的实施顺序，两项仍同为 P0，不把后一项降级或拆出本次交付。
