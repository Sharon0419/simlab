# SimLab 0.3.0 — 基地换 LRU 与站内 SRU 维修

## 本版交付

采用用户选定的两级维修方式：基地换下整件 LRU，故障模块送修理站；站内检测、拆换 SRU、测试，合格模块返库。系统恢复和模块维修是独立流程。有备用模块时，设备可以先恢复任务。

使用“项目概览 → 新建多层维修示例”。原项目保留，新示例另存为独立项目。可查看“组成结构”，编辑 SimLabDepotProcess 中检测和测试时间，在“仿真实验”运行；“结果分析”新增维修统计、工序耗时和部件实例。“维修 CSV”导出首轮工单明细。

便携包：`dist/SimLab-Windows-v0.3.0.zip`；直接双击 `启动SimLab.cmd` 或 `dist/SimLab/SimLab.exe`。升级后先关闭旧窗口再打开。examples 目录包含连续保障、任务日历和多层维修三套模型及含结果项目。

## 输入映射

| 内容 | 表与字段 |
|---|---|
| System→LRU→SRU | MaterielStructure.MMID/MID/QTYPM/ENVF |
| 叶子故障 | Item.TYPE=LRU 或 SRU，FRT/AFFRT；仅 OPHOURS、CRIT=1 |
| 基地 LRU 拆装 | ItemReplacement，MID=系统，IID=LRU，STID=基地 |
| 站内 SRU 拆装 | ItemReplacement，MID=LRU，IID=SRU，STID=维修站 |
| 叶子直接维修 | ItemRepair，IID=叶子，DIRPT/DIRPTID；SURPT=0 |
| 检测与测试 | SimLabDepotProcess，LRU/STATION/DIAG_H/DIAG_TASK/TEST_H/TEST_TASK |

原字典的 133 表、891 字段保持不变。SimLabDepotProcess 是单独标识的扩展表，增加 6 个字段；扩展版本为 1。检测和测试是固定时长，其任务字段引用 Tasks/TaskResource。0 小时仍会申请所配资源；同时留空任务才不等待资源。

带子件的 LRU 要求 FRT=0、AFFRT=1，不能又配置 ItemRepair 整件直接维修。叶子 SRU 的 FRT、AFFRT 和父子结构 ENVF 共同形成故障强度；系统/LRU 的 ENVF 继续缩放整组叶子。无 SRU 的 LRU 仍走直接维修。组成超过 System/LRU/SRU、循环、缺少工序或修复规则会被拒绝。

## 实物与故障时钟

每台设备内和每件备用 LRU 内都建立真实子件实例。SRU 的 StockAllocation 数量是额外散件，不包含这些已安装子件。父件运输时子件保持附属关系，物理位置随父件变化；拆下后才进入散件维修或库存。实例移动和安装检查父子唯一性、类型、库存与装机重复；每次重复试验末检查实物总数和每类数量守恒。

层级模式为每件叶子保存指数危险度预算，在设备实际运行时按故障强度扣减。待命和停机暂停，健康叶子不会因其他件故障而重新抽样；故障件修复后下次使用重新抽样。不含层级的模型保持旧算法路径和旧示例数值。

## 维修流程

故障 → 基地拆卸 → 整件送修 → 检测 → 内部拆卸 → 等待健康 SRU → 内部安装 → 测试 → LRU 返库。

坏 SRU 被拆下后同时启动独立的直接维修；散件可用时，父 LRU 不等待坏件修完；没有散件时可以等这件修复返库。父件只有必要安装位置完整且叶子健康，并完成测试，才能返库。

每个工序分别申请整组资源。检测、内部拆卸结束释放资源，等待 SRU 不占用工位和人员。资源按原站点 FIFO，班内启动，已开始允许跨班完成；下一工序重新检查班次。运输不占维修人员。本版使用既有两级保障补充逻辑，不增加采购、横向调拨或运输容量约束。

## 输出口径

- **维修周转**从基地拆卸结束、启动送修开始，到该部件在维修站返库；不包括基地拆卸、回基地补充运输和系统安装。只对已完成工单求均值，避免把未完成当作短维修。
- **工序耗时**为各重复试验的工单耗时总和的均值，包含未完成工单截至仿真终点已发生的时间；不是每件平均工序时长。
- **LRU/SRU 分组**中 LRU 包含直接修复模块和内部换修模块。父件等待 SRU 与子件维修会在各自工单中同时计时，不能把两个层级的耗时相加解释为设备停机时间。
- **部件实例**为首轮终点状态，最多 1000 条。故障 LRU 在内部子件修好、测试尚未完成时仍标记待修复。
- 运输中实例显示的站点是目的地；附属子件的物理流程和站点跟随父件。
- **维修 CSV**为首轮工单样本，最多 1000 工单，含运行标识、模型哈希、种子、父件、站点、起止和工序小时。总量统计覆盖全部工单；截断样本不能代替完整审计轨迹。
- 可用度和任务满足率保持 0.2 的独立口径；真实业务校准与原厂任务成功判定对照尚未完成。

## 验证基准

确定性测试令首次故障发生在第 5 小时：

| 场景 | 期望 |
|---|---|
| 无库存、无运输：基地拆1＋检测1＋内部拆1＋SRU修4＋内部装1＋测试1＋基地装1 | 第15小时恢复，停机10小时 |
| 备用 LRU 一件 | 第7小时即可恢复；首个故障 LRU 第14小时才返库 |
| 备用 SRU 一件 | 设备第11小时恢复，坏 SRU 第12小时才修完 |
| 两套故障模块共用一名内部拆装修复人员 | 按 FIFO 手算，两台设备第20、21小时恢复 |
| 检测第7小时结束，内部拆装资源班次0–7及12–30 | 内部拆卸等到第12小时；设备第20小时恢复 |
| 仿真截止第10小时 | 父件工单未完成，不给已完成周转均值；已累计工序4小时 |
| 零故障 | 可用度1、零维修工单 |
| 两种叶子首次预算1、2，故障率0.2、0.1 | 第5小时第一件故障，健康第二件剩余预算1.5，不重抽 |

另测结构拒绝、深度与循环、父 LRU 重复故障率拒绝、附属子件不可独立移库、重复安装拒绝、固定种子复现和扩展项目交换。旧36项测试继续保留。

## 兼容性与下一步

项目数据库格式继续为1，另记录 extensions_version=1，拒绝不支持的扩展版本。旧项目可打开并保存；老版本遇到新扩展表会明确拒绝。没有二进制原厂文件兼容承诺。

本次只实现选定的两层纠正性维修。计划性维修、寿命老化、冗余、更多层级、复杂任务规则和多级供应仍未实现。下一阶段应先冻结预防维修触发、到期工单与纠正维修冲突规则，再增加实现。
