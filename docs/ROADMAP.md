# SimLab 向 SIMLOX 靠近的开发路线

日期：2026-09-07；状态：建议方案，未排定工期。

进度更新：0.2 已交付 M0 的实现验证基线和 M1 的最小任务日历闭环；真实业务校准仍待数据。下面保留总体能力规划；下一步实施以 [0.3 多层维修计划](NEXT_VERSION_PLAN.md) 为准。

目标：先做能解释和验证的动态保障仿真，再扩大业务覆盖。当前已有桌面、项目文件、基础故障维修与两级供应；字段覆盖不等于规则覆盖。

## M0 建立可信基线（P0）

确定对标版本、业务场景、单位和统计口径；建立能力矩阵与最小基准案例。

验收：至少 10 个确定性/解析案例通过；随机案例按预先约定的误差与置信区间比较；每个差异都有解释。

依赖：起点。建议角色：业务负责人 + 仿真开发，未指派人员。

## M1 任务与时间变化（P0）

任务需求、开始结束时间、设备分配、运行/待命状态、人员班次；输出任务满足率和缺口。

验收：固定任务案例可逐事件手算；换班边界不超配资源；可用度与任务满足率分别计算。

依赖：依赖 M0。建议角色：仿真开发 + 界面开发，未指派人员。

## M2 多层维修与计划维修（P1）

LRU/SRU 层级、维修路由、维修资源、定期检查；随后分开实现年龄相关故障与维修后年龄更新。

验收：父子部件守恒；维修占用和设备恢复时刻符合手算；不能产生循环维修或无依据的瞬时恢复。

依赖：依赖 M0；日历维修依赖 M1。建议角色：领域专家 + 仿真开发，未指派人员。

## M3 多级供应与扰动（P1）

多级仓库、补货策略、运输能力、采购报废、供应中断；再增加横向调拨。

验收：每种部件的期初量加采购减报废等于期末各位置合计；无负库存、重复发货和无限制运输。

依赖：依赖 M0；返修供应衔接 M2。建议角色：保障业务专家 + 仿真开发，未指派人员。

## M4 系统能力与冗余（P1）

串并联和 k-out-of-n 结构、非关键故障、降级能力；绑定任务能力要求。

验收：简单结构与解析结果一致；冗余失效和修复转换正确；设备可用不自动等于任务可执行。

依赖：依赖 M1、M2 的状态语义。建议角色：可靠性专家 + 仿真开发，未指派人员。

## M5 批量试验与决策（P2）

参数扫描、敏感性分析、成对比较、目标达成概率；成本口径明确后再做成本性能权衡。

验收：同一方案可追溯复现；方案差值报告不确定性；独立重复并行后随机流身份保持稳定。

依赖：基于已验收引擎；先小规模扫描。建议角色：仿真开发 + 分析人员，未指派人员。

## M6 产品化与团队使用（P2）

模型树和网络编辑器、能力提示、数据迁移、报告、性能剖析；多人需求明确后增加服务端作业系统。

验收：旧项目迁移不丢字段；结果可追溯；在约定设备规模和硬件上验证耗时与内存。

依赖：持续改进；服务化按需求启动。建议角色：产品开发 + 测试，未指派人员。

## 下一版建议

M0 + M1 最小闭环已在 0.2 实现。下一版建议实现 M2 的多层纠正性维修子集；计划性维修与老化分别在后续阶段冻结规则后实施。

## 用户需要准备

一个优先业务场景；对标的 SIMLOX 版本；设备和部件结构；带运行暴露量的故障记录；维修、库存、运输记录；任务和班次计划；可获得的同口径原厂结果。若没有原厂结果，以解析基准和历史数据校准分别验证实现与现实适用性。

## 架构推进

保留 Qt、独立 worker 与 SQLite。逐步形成任务/设备状态、维修流程、供应网络、随机分布、统计收集模块；编译层统一转换带单位的类型配置，并记录引擎与模式版本。不以放开 compiler 支持检查代替业务规则实现。

## 产能与缓冲

团队、可投入时间和数据均未明确，因此没有可靠日期或人天估计。建议每个阶段拆成可验收的小增量，排期时预留约 20% 给校准和回归。上述角色可由同一人兼任，但业务口径需要用户或领域专家确认。

## 风险

- 高：模型语义不一致。先签定单位、故障时钟、预热期、任务成功和维修规则。基准未通过则不进入下一层功能。 负责角色：业务负责人。
- 高：真实数据不足。先用标注清楚的合成案例验证机制；缺历史数据时不宣称预测准确。 负责角色：数据负责人。
- 高：范围一次铺得过大。下一版只交付 M0 与 M1 的最小闭环，复杂调度和高级优化后移。 负责角色：项目负责人。
- 中：规则扩展使引擎耦合。按任务、维修、库存和统计拆分边界；每次新增规则增加解析或守恒验证。 负责角色：技术负责人。
- 中：仿真规模膨胀。先剖析事件数量和内存，按独立重复试验并行，不预先重写 C++。 负责角色：技术负责人。
