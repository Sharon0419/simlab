# SimLab 0.2.0 — 任务日历与维修班次

2026-09-07。本版完成 M0 的解析/确定性验证基线与 M1 的最小任务日历闭环。真实数据校准和原厂结果对照仍需要用户业务数据；不声称完整替代 SIMLOX。

## 启动与体验

双击根目录 `启动SimLab.cmd` 或 `dist/SimLab/SimLab.exe`。软件已有窗口时先关闭旧窗口，再运行更新后的版本。便携包为 `dist/SimLab-Windows-v0.2.0.zip`，解压后保留整个 SimLab 文件夹，无需安装 Python。

1. 进入“项目概览”，点击“新建任务日历示例”，创建独立项目，不覆盖当前模型。
2. 示例有 20 台车辆，30 天内每天 08:00–16:00 需求 15 台；基地和修理中心的维修人员每天 08:00–17:00 允许开始作业。
3. 进入“模型数据”，修改 MissionType.NOS 与 MNOS，两者保持一致。改为 22 可观察部署数量不足的缺口。
4. “仿真实验”校验并运行；在“结果分析”切换上方“任务供需”、下方“任务窗口”和“任务缺口”。
5. 可修改 ResourceAllocation 数量或 ShiftProfile 班次再运行，通过“实验对比”比较任务满足率；“导出任务 CSV”导出各窗口的均值结果及追溯信息。

若延长仿真期，需要在 OperationProfile 和 ShiftProfile 显式增加相应日期；缩短仿真期需要删除越界任务窗口。计划是绝对小时，不自动按日重复。示例及其含结果版本也放在便携版 examples 中。

## 功能和字段契约

原字典仍为 133 张表、891 字段，项目格式仍为 1。使用原字段的受限子集，不新增冒充原厂的字段。0.1 项目可直接打开；0.1 结果没有任务指标时界面显示“无任务日历”。

| 对象 | 支持字段与限制 |
|---|---|
| MissionType | MTID、NOS、MNOS、MNOSA、DURN；NOS=MNOS，MNOSA 留空或同值；DURN 固定正小时 |
| MissionSystem | 每种任务只能指定一个 SID；数量字段留空或与 MissionType.NOS 一致 |
| Operations | USTID 为站点或单位，PRID 引用运行剖面；站点任务可使用该站点下符合系统类型的设备 |
| OperationProfile | PRID、SPRID、STIM；SPRID 直接引用任务类型，STIM 为绝对小时；每行一个窗口 |
| Shift | SHID 定义班次名称 |
| ShiftProfile | SHPID、SSHPID、STIM、ETIM；直接引用 Shift，结束大于开始；重叠/相邻班次合并 |
| ResourceStationData | RID、STID、SHPID 绑定已配置资源与班次；未绑定的资源全天可用 |

默认值限定：MPAT=FIXED，PRI=1，IQTY=1；不支持随机任务时长、递归剖面、再生/随机启动、延迟启动、按不同最小数量中止任务、复杂优先级。改变这些规则的非默认设置在运行前拒绝，不静默忽略。

任务模式要求全部部署 UTIL=1；若没有 Operations，保持 0.1 的连续使用率语义。单次任务需求不超过 2000 台，任务窗口最多 2000 个，窗口数×重复次数最多 200000；班次合并后最多 10000 个。

## 调度与时钟

任务是固定需求窗口：[STIM, STIM+DURN)。按开始时间、任务标识排序，先到先服务；不抢占已有任务设备。设备选择使用稳定的部署顺序。每台设备最多同时服务一个任务。

任务开始时尽量分配设备；数量不足仍保留整个需求窗口并累计缺口。设备故障立即退出，空闲可用设备可即时补位，不建模任务地点间赶赴时间。设备修复后可以补缺；任务到期释放设备。这里的固定窗口不是原厂完整任务执行/中止模型。

任务期间以每小时一个运行小时累计故障，待命不累计；拆装或故障停机也不累计。剩余指数故障时钟跨待命与任务切换保留，维修完成后重新抽样。任务开始/结束同一时刻按当前有效窗口重新分配，不产生正时长的虚假缺口。任务超过仿真终点会在校验时拒绝，结束恰等于终点允许。

维修组合资源仍按站点 FIFO 原子申请。所有需要的资源都在班内且有空闲数量才能开始；已开始的维修或拆装不抢占，可跨班完成。拆卸和安装分别申请，所以跨班完成拆卸不代表可以班外开始安装。无共同班次的资源组合会被拒绝。班次不会暂停运输。

## 输出与数学口径

- **可用度**：设备处于可用状态的总设备小时 / 全部设备日历小时。待命和正在执行任务都属于可用，不等于任务满足率。
- **设备小时满足率**：所有任务实际供给设备小时之和 / 所有任务需求设备小时之和。需求不足不会缩减分母。
- **缺口设备小时**：需求设备小时减供给设备小时。
- **全程无缺口窗口比例**：整个需求窗口内没有正时长缺口的窗口占比（浮点判定容差 1e-9 设备小时）。不是随机抽取某时刻的满足率，也不是原厂任务成功率。
- **均值 95% 区间**：基于独立重复试验满足率的 Student-t 近似；单轮不给区间。
- **资源占用率**：占用资源小时 / 配置数量×整个仿真日历小时，含跨班加班占用，不是“在班利用率”。

指标在任务边界、故障、维修状态变化时精确积分。曲线只按 RCINT 采样，可能漏掉短时需求或缺口，不能从图上点均值推算整体满足率。窗口级 CSV 包含模型哈希、运行标识、种子、需供设备小时与全程无缺口比例。

缺口原因分为部署数量不足、其他任务占用、等待备件及运输、等待维修资源或班次、拆装作业。每个窗口先计部署不足，其余按稳定设备顺序归集不可用设备状态，合计严格等于缺口。该归集是描述性分摊，不是因果贡献排名；同一故障可能同时影响多个并发任务的需求，这是按任务需求计量的结果。

## 可手算/解析验证基线

| 案例 | 期望 |
|---|---|
| 零故障、2 台供 2 台需求、4 小时 | 需求=供给=8 设备小时，满足率 100% |
| 零故障、1 台供 2 台需求、4 小时 | 需求 8、供给 4、缺口 4，满足率 50% |
| 3 台供 2 台需求 | 多余设备不产生额外供给，满足率不超过 100% |
| 1 台、窗口 0–6 与 2–8 | 第一任务供给 6、第二供给 2，竞争缺口 4 |
| 同一设备、窗口 0–6 与 6–12 | 无重叠占用，满足率 100%，终点窗口计入 |
| 任务在第 10 小时才开始 | 第 10 小时前无运行故障 |
| 第 2 小时故障，另一台即时补位 | 没有正时长的供给缺口 |
| 全部不可用 3–5 小时 | 精确缺口 2 设备小时，恢复后补位 |
| 首次故障需 3 运行小时，任务 0–2 和 10–12 | 故障发生在第 11 小时，待命不耗时钟 |
| 班次 2–4、8–10，先修 4 小时再修 1 小时 | 作业开始 2 和 8，结束 6 和 9 |
| 组合资源班次分别 1–7、3–9 | 最早启动在第 3 小时，资源同时占用 |
| 组合资源无重叠班次 | 编译拒绝并指出共同班次问题 |
| 错误系统类型的设备 | 不计入任务供给 |
| 无备件单机，平均正常 100 小时、固定修复 20 小时 | 长期可用度接近 100/120，允许绝对误差 0.012 |

另外验证固定种子复现、部件守恒、输入拒绝、项目与交换包往返，以及长日历故障时钟浮点余量回归。桌面端到端验证同时覆盖旧连续模式和新任务模式。

## 架构与本地 Git

`operations.py` 编译任务窗口与班次；`missions.py` 负责分配与积分；`engine.py` 处理运行故障时钟、修复和班次资源门控；worker、JSON 通信和 SQLite 项目结构继续沿用。

本地基线提交为 `c6a9968`，标签 `v0.1.0`。开发分支为 `codex/v0.2-missions-calendars`，完成后标记 `v0.2.0`。仓库只在本机，未配置或推送远程。`.venv`、构建产物、运行数据库、用户项目和临时文件不入库。

查看历史：`git log --oneline --decorate`。对比版本：`git diff v0.1.0 v0.2.0`。需要查阅旧代码时可使用 `git show v0.1.0:simlab/engine.py`，不必改动当前工作目录。

后续仍需实现多层维修、任务能力降级、冗余、预防维修、供应中断等，并用真实保障数据校准。本版本限定为固定需求窗口、单系统任务和维修启动班次。
