# M3 三级供应与维修方式执行设计

日期：2026-09-16。基线：v0.9.2 / `934e666`。

状态：设计待整体评审，未实现。用户已授权根据讨论完善执行设计；已确认业务规则见 [讨论汇总](../../M3-DISCUSSION.md)。本文中的“设计默认”是为闭合执行语义提出的方案，不冒充此前用户已逐项确认。测试表为未来验收预言机，不是已通过结果。

## 1. 范围与交付顺序

拆成两个顺序增量，使用同一实物与订单模型：

1. **M3-A：供应闭环**。三级地点、显式调运策略、临界库存/周期触发、目标库存、多来源最短时长选择、拆分、缺货等待、维修返库与订单联动、中文输入及结果。
2. **M3-B：维修分流**。修复性/预防性原位与换件、独立比例与作业参数、部件预防性时钟、年龄及父子实物处理。

M3-A保留原有纠正性换件方式，但维修目的地改为显式映射；通过后再接入M3-B。最终本轮交付要求两者都通过，不能把M3-A完成当成用户全部维修需求已完成。

两个增量是内部验证节点，本设计只安排一次完整对外交付和一次扩展格式升级。若中途对外发布M3-A，M3-B须另升扩展格式版本，不能让同一个版本号代表不同字段集合。

首版调运有货即可发运，仅计固定运输时间，无容量约束。采购、报废、供应中断、横向调拨、运输容量、跨基地装备转移和自动优化不在本轮实现中；属于原M3后续能力。没有真实数据校准或原厂数值等价结论。

选择：新模式使用一个供应订单服务和一个维修协调器，旧模型保持原有执行分支。

备选“在replenish中递归找上级”无法表达多来源候补、唯一申请和周期补货；备选“全面替换旧引擎”扩大回归风险。因此新服务按显式模式启用，逐步接入既有组件、资源池和任务状态，不重写全部系统。

原字典已存在ItemStationStructure、CMStationStructure、PMStationStructure、MaterielPM、PMReplacement、TransportPolicyProfile及比例字段，但字段同名不等于语义一致。本设计采用SimLab扩展，不修改原133表891字段，不将原厂ENPM/OPOL等字段解锁为完整支持。原厂手册逐项语义对照不属于本次已完成证据。

## 3. 已确认规则及设计默认

已确认的规则全部保留：三级组织、显式策略才允许跨级、短调运优先、无货候补、允许拆分、全缺货保留申请、库存位置补到目标、两种触发互斥、公共返库、维修概率分流、缺件不改维修方式、两类维修参数独立、预防性修复如新、运输不设容量。

为形成可执行设计，提出以下默认值，评审时可直接调整：

| 编号 | 设计默认 | 影响 |
|---|---|---|
| D1 | 临界模式在库存位置≤临界值时触发；目标值必须大于临界值；初始化也检查一次 | 边界确定，避免零量反复触发 |
| D2 | 周期模式显式FIRST_H、INTERVAL_H；FIRST_H默认0，可改；每个周期补到目标值；期末不再生成新申请 | 不把所有周期强制从一个周期后开始 |
| D3 | 首版调运时间固定小时，可为0；同长策略按稳定策略ID排序 | 可复现，不随机抢货 |
| D4 | 不同需求按创建时刻、稳定请求序号先到先服务，允许部分满足；无任务优先级抢占 | 竞争库存结果确定 |
| D5 | 原位作业在当前安装地点执行；拆下件由明确的维修站映射决定目的地 | 不隐含运送整架装备 |
| D6 | 故障件、预防性拆下件的送修路线显式配置；不自动反转补给路线 | 方向、时长独立，不凭空创建路径 |
| D7 | 部件预防性首版作用于叶子件，支持日历经过小时或有效运行小时；作用于实物，不作用于安装槽位 | 带子件总成的整体预防翻修暂不开放，避免擅自清零全部子件 |
| D8 | 空中预防到期不单独中止，落地后执行；到期停派；同件一张未完预防工单，完成后新周期 | 与故障返航规则区分 |
| D9 | 供应请求一旦生成不因后来修复入库或候补来源变化自动撤单；其数量始终进入未到货量 | 不重复申请，但短期库存可能高于目标值；目标是订货目标而非库存硬上限 |

D7包含装在LRU内的叶子SRU，必须有其实际作业地点对应的拆装/原位资源配置；不允许悄悄搬走整机。用户已确认的比例及预防性流程不变，只明确首个可验证的作用对象。

## 4. 输入与字段契约

以下为拟新增字段，尚未写入schema。ID为稳定文本，时间统一小时，数量为非负整数，所有数值必须有限。配置表中不保存运行订单。

### 4.1 模式、地点与供应

| 扩展表 | 主键及字段 | 语义 |
|---|---|---|
| SimLabExecution | MODE | 单行；新增模式M3。无此行沿用旧模式 |
| SimLabSupplyRoute | ROUTEID；IID、FROM_STID、TO_STID、TRANSIT_H | 按部件配置有向补给策略，严格从高层到其后代，可跨一层；禁止同级、逆向及重复同起终点同部件 |
| SimLabSupplyPolicy | POINT、STID、IID；TRIGGER、TARGET_QTY、REORDER_QTY、FIRST_H、INTERVAL_H | TRIGGER=THRESHOLD/PERIODIC；按Control.APID选择方案。同仓同件只有一行；无关模式字段留空 |
| SimLabRepairLocation | IID、FROM_STID；REPAIR_STID | 每类件在每个实际拆卸来源唯一映射到维修站；允许本站、祖先站；不由最短补给时间决定维修地点 |
| SimLabServiceRoute | ROUTEID；IID、FROM_STID、TO_STID、TRANSIT_H | 独立有向送修边；严格由低向高，同站维修无需边 |

Station/Unit/SystemDeployment继续定义地点及部署。StationStructure在M3模式仅定义单父三级树；深度不超过3，显式调运表覆盖运输定义。M3模式下StationStructure的TFRMS/TTOMS等运输字段仅接受默认零，不混用隐含路线。无新模式时保留原两级约束及旧时间解释。

StockAllocation按选用POINT的ISTOH（空则STSIZ）创建初始实物；STSIZ不自动变成补货目标，补货目标只来自TARGET_QTY。初始库存件为健康新件；每个装机实物沿用已有年龄初始化。最高层允许无补货策略，仅由初始库存和修复返库供货，不隐式采购。

任何需要外部补货的策略必须至少存在一条匹配入向SupplyRoute。中间供货站如需要继续向上补货，必须另设自己的SupplyPolicy；单有地点层级不生成补货。编译报错需定位表、行、部件和站点。

### 4.2 维修与预防性触发

| 扩展表 | 主键及字段 | 语义 |
|---|---|---|
| SimLabMaintenanceRule | RULEID；MID、IID、STID、KIND、METHOD、REPLACE_P | MID为直接母项System或Item，STID为实际安装/作业地点，KIND=CORRECTIVE/PREVENTIVE；METHOD=IN_PLACE/REPLACE/MIXED，概率0～1仅MIXED必填；同上下文唯一 |
| SimLabMaintenanceStep | RULEID、STEP；DURATION_H、DISTRIBUTION、TASK | STEP=DIAGNOSE/IN_PLACE/REMOVE/INSTALL/TEST；时长和资源独立，固定或指数分布；未使用工序不允许配置，必需工序可显式0小时 |
| SimLabOffItemService | IID、STID、KIND、STEP；DURATION_H、DISTRIBUTION、TASK | 叶子拆下件在维修地点的DIAGNOSE/SERVICE/TEST作业；与原位及拆装分别配置 |
| SimLabItemPreventive | PMID；IID、CLOCK、INTERVAL_H、INITIAL_H | 每类叶子一条；CLOCK=CALENDAR/OPERATING；间隔至少1e-6小时；首次装机周期已用值默认0，初始库存为0 |

每个PREVENTIVE规则必须能匹配预防时钟及全部可到达作业地点。预防性换件后的维修目的地和送修路线必须存在。拆下件服务不再次抽“换件比例”，防止同一层无限递归。

新模式下直接SRU/LRU使用上述规则；带SRU的LRU按下节的递归语义处理，禁止给父LRU配置“整件SERVICE后全部清零”来绕过子件。原有ItemRepair/ItemReplacement/SimLabDepotProcess可在M3-A使用已验证语义；M3-B的迁移工具生成显式新规则。若同一上下文同时存在新旧非等价规则则报错，不静默决定优先级。迁移必须显示字段来源与差异后生成新项目副本，不改写原项目。

## 5. 库存、申请与唯一记账

### 5.1 三种记录

- **Demand**：本地装备/维修取件需求，或唯一转交到本站的下游请求份额。记录创建序号、数量、已满足数量、请求对象。
- **Order**：接收站一次补到目标的申请。包含OID、站点、IID、触发时刻、总量Q、待分配U、在途T、已收货R，以及每段数量的来源分配。始终Q=U+T+R；一期末保留未完部分。
- **Shipment**：一批实际发出的实物ID清单、唯一OID、路线、发货/到货时间和数量。仅分配记录不生成实物，发货原子地从库存取出实际件。

库存位置IP=A+O−B：A为可用且未预留实物，O为本站所有未收货订单的U+T，B为本站尚未满足且未预留的需求。维修中的件不计可用，也不计未到货订单；修好入库后才进入A。已预留件既不在A，也不在B，不能双扣。

补货提交时一次性将Q加入O，随后才能分配；零量不建单。入库减少T、增加A，立即服务等待需求时再减少A和B。各量变化只有供应服务能提交，UI及维修协程不能分别改计数。

### 5.2 最短策略与多级缺货传递

1. 对同一待分配请求，枚举直接进入目的地的已配置策略，按TRANSIT_H、ROUTEID排序；不把a→b和b→c自动拼成a→c直达。
2. 按序从有库存来源分配min(剩余需求, 可用数量)。每批发货立即把目的地订单U转T，登记唯一实物与到货事件。
3. 剩余U仍为一个申请，不为每个候选来源复制整单。为使中间层能识别缺口，将这部分U**仅记到最短策略来源的一份转交需求**；这只是记账归属，不是锁定供货来源。它减少该来源IP，按该来源自身触发策略补货。
4. 所有合法候选来源的入库都会唤醒该请求。另一来源能供货时，先撤销原来源对应数量的转交需求，再在真实来源登记及发货；整个数量转移为同一无yield事务。原来源归属不妨碍用户确认的有货候补。
5. 若缺货继续向上，逐层采用同样规则。供货边严格下降、需求传递严格上升，最高层停止，不凭空采购、不负库存。
6. 真实来源发货后，按其库存变化运行自己的补货策略。PERIODIC只在该站周期到点新增订单；THRESHOLD按事件检查。已经存在的待满足订单不受新周期限制。

例：c缺1件、b缺货，只有b→c、a→b。c的一份申请在b登记一份需求；b自己的策略触发后向a申请。a的件先实际到b，再由b发往c。c不在a处另记一份直接供货需求。

候补切换后，原来源已生成的上游订单按D9保留；因此以后可能形成额外可用库存，但不是原请求被重复履行。报表须显示这种在途承诺，不能承诺TARGET是硬上限。若需要自动撤单或改目的地，将另设策略，本轮不隐式实施。

### 5.3 原子性与事件顺序

同刻按以下阶段执行到稳定：结算到货/已完维修入库 → 服务既有需求 → 注册本时刻新需求/周期触发 → 检查临界策略并登记新订单 → 分配及发货。每阶段采用稳定序号；所有检查读取同一已提交账本，不在申请中途yield。

零运输时长仍通过一个可追溯到货事件完成，不能把发货和到货合并为无记录的计数变化。用严格有向层级、唯一请求数量及零量禁建单保证同刻收敛；若超过运行规模上限，报明确失败，不能截断物理计算后继续报成功。

## 6. 维修执行与实物年龄

### 6.1 决策与作业

每个维修工单有独立JID、KIND、目标实物ID、直接母项、实际站点、触发原因和关联需求。触发时抽一次维修方式并持久到工单；单一方式和概率0/1不消耗抽样。等待、重试、缺件、换班不重抽。

- 原位叶子：必要检测→等待人员设备→原位作业→测试→服务完成。实物不进公共库存，作业期间不能派遣装备。
- 换件：拆卸→原实物进入送修/工单隔离状态→为安装建立本地取件需求→等待可用件→安装→测试。送修与装备等待/恢复异步。
- 拆下叶子：按明确送修边到维修站→检测→对应修复性/预防性作业→测试→服务完成→公共返库。送修多段选配置边上的最短总运输时长路径，同长按路线ID序列排序；不能利用补给边的反向推导。
- 无备件时等待，不持有拆装资源。工序按组合资源申请，班内启动、允许跨班完成，沿用既有资源池语义。

修后测试计入该次服务；年龄更新在全部必需作业/测试完成时发生，期末仍未完成不能提前归零。装入的库存件保留自身已有年龄；不是所有换入件都当新件。

### 6.2 多层部件

系统直接装机LRU的方式先按其上下文选择。带子件LRU：

- 选择原位：LRU保持装在装备上，对实际故障叶子在当前地点逐项处理，可按叶子上下文执行原位或内部换件，完成父项测试后恢复。
- 选择更换：LRU整体拆下送指定维修站；在站内对故障叶子逐项按其规则处理。整个LRU和其仍附着的子件作为一个运输单元，不把子件再计入散件库存。
- 叶子SRU被换下后是独立实物，可有自己的维修地点。父子关系必须通过detach/attach更新；禁止直接搬运attached实物。
- 父级测试不清零健康兄弟件年龄。所有故障叶子按稳定槽位顺序处理，保留当前串行原则；不同装备可并发竞争资源。

新增叶子预防性原位/换件在其当前安装地点执行；父LRU及装备在作业期间锁定，不能同时对同一父子树启动另一作业。首版不开放带子件LRU整体预防性年龄重置。

嵌套工单继承已有父子树锁，不再次等待自己持有的锁；子件拆下后退出原树锁的覆盖，独立送修。父件等待子件期间释放工序资源，但保留防止并发拆装的逻辑锁。这样既可异步修子件，也不会递归自锁。

### 6.3 预防性时钟与冲突：设计默认

每个实物叶子记录各自预防性周期已用小时，与有效故障年龄和终身小时分离。OPERATING按实际运行×UTIL累计，含故障返航中的健康运行；待机、运输、库存、维修暂停。CALENDAR按经过时间累计，库存和运输也计时，进入该项服务后暂停；INITIAL_H是周期初始值，不自动等于故障年龄。

初始周期值达到间隔时在t=0登记到期，不取模抹去超限。M3-B统一维护全部叶子的运行小时，即使该件未配置Weibull；没有老化规则仍按Item.FRT计算指数风险，不为了记录运行小时强制用户改故障分布。旧模式的老化启用条件保持原样。

CALENDAR库中件到期即从可用库存移出，建立服务工单；在途件到期保留运输、到货后隔离服务，不可拿去安装。订单物理收货仍按实物到达完成，因不可用导致的新补货按本站策略处理，不能伪造可用到货。运行周期库存件不增时，但已有到期标记同样不可发出。

同件同规则最多一张未完成预防工单。到期登记并停派，空中到期记超限但不单独中止；故障仍按原中止返航逻辑。既有准备及已开始维修不抢占，落地后共享装备维修锁。待执行工单采用纠正性优先，其余按到期时间、类型（日历整机→飞行检查→部件预防）、规则ID排序；新故障不打断已开始工序。

若同件预防工单尚未开始即发生故障，保留两个原因，但先执行纠正性：PERFECT已对同件完成修复如新时，待执行预防单记为covered_by_corrective并重启该周期，不重复作业；MINIMAL不覆盖，仍执行预防单。若预防服务已在执行，健康检查不另造故障。覆盖、取消和实际完成分开统计。

服务完成后本项周期归零。預防服务对实际叶子强制PERFECT，清有效年龄及旧风险预算，保留终身小时；不得受该件纠正性MINIMAL配置影响。叶子健康也可预防服务，因此必须新增明确的preventive完成方法，不设置broken=True来借用restore。

所有地面工单清空后统一一次必要准备，保持每日首波假设不能跳过真实维修后准备。原有SimLabPlannedMaintenance及SimLabFlightInspection不改为清龄作业，也不自动生成部件预防工单。

## 7. 模块接口与兼容

建议按职责增加模块，而不是继续把新规则全部放入engine.py：

| 模块 | 职责与接口草案 |
|---|---|
| supply_config.py | compile_supply：树、路线、策略、目的地及规模校验；纯输入编译 |
| supply.py | SupplyNetwork：request_part、return_part、tick_policy、allocate、snapshot；唯一库存写入口 |
| supply_ledger.py | Demand/Order/Shipment及数量守恒；分配/归属转移无yield事务 |
| service_config.py | 编译作业步骤、分流、资源和预防时钟；校验全部可到达上下文 |
| service.py | ServiceCoordinator：建立工单、抽方式、装备/父子树互斥、调用供应和资源服务 |
| preventive.py | 实物预防时钟、到期标记、暂停/完成；不自行调拨库存 |
| components.py / aging_components.py | 实物move/detach/attach、年龄结算和明确的服务完成事件 |
| engine.py / maintenance.py / flight.py | 组装新服务，故障/落地/准备衔接及期末结算；旧模式不调用新调度 |
| supply_results.py / service_results.py | 纯结果聚合、CSV；不触发随机数、调度或状态变化 |

接口返回结构化事件和稳定ID，不向UI暴露SimPy Store内部队列。旧Workshop的取件/返库通过适配层接入新模式，不能两个模块同时持有同一库存的写权限。

随机流：现有failure/repair/replace标签0/1/2保持。新模式按独立标签增加维修方式与预防作业流，版本固定映射并写入结果。固定运输不消耗随机数。旧模式不初始化/调用新增流；新模式不保证与旧模式逐样本相同，但同一版本输入/种子可重放。

拟使用扩展格式10：读取1–9，保存/导出升级但保留历史runs原始内容；真实版本9读取器明确拒绝10。MODE决定运行语义，不能仅凭保存格式切换到M3。所有新增表、字段中文标签、枚举值显示、分组、验证、CSV和交换同时交付。

规模上限沿用现有2000台装备、200000件初始实物、1000轮和10000采样点；新增每轮最多200000份订单、200000份服务工单、1000000批运输记录。编译时对周期触发能计算的上界提前拒绝；运行时对动态超限停止该轮并记录失败原因，不返回部分结果为成功。显示明细截断不影响内部账本或守恒检查。

新模式针对原有连续运行、固定任务/值守、固定飞行都须验证。飞行增加落地限制；其余模式可在到期时停派，已开始工序不抢占。若实现中无法完成某种模式，必须收缩并评审范围，不能默默沿用不适用的飞行代码。

## 8. 结果与守恒

中文页面提供：各站各件可用/预留/维修/在途、库存位置与目标、申请状态、各路线发货和到货、缺货等待、原位/换件选择及实际完成、修复性/预防性工单、年龄前后和超限小时。

“方式选中次数”和“实际完成次数”分列；抽样比例不要求小样本精确等于输入。装备等待备件与备件自身运输时间不直接相加为系统停机，避免并行过程重复记账。无运输容量等待指标伪装成已支持能力。

每轮强制校验：

- 每类实物期初数=期末各互斥物理位置数之和；附着子件按实际位置展开一次，不和散件双计；无采购报废增减项。
- 每个实物只有一个位置/父槽位，不同时在库、装机和运输；所有待发/可用件健康且无到期服务标记。
- 每单Q=U+T+R，批次数量等于实物清单长度；一个实物同时最多属于一个未完成批次；待分配转交份额总和等于U，不能多来源复制。
- 每项服务完成的年龄变化可追溯，终身小时不减，健康兄弟件不受影响；尚未完工不提前更新年龄。
- 每架设备的互斥状态时间之和等于仿真观察时长；期末在途、缺货、维修未完保留，不假装完成。

CSV含轮次、模型哈希、版本、种子、OID/JID/批次ID/实物ID。明细保留策略初定每轮每类最多10000条，并记录总数、保留数和截断标志；全轮摘要不截断，守恒检查用完整内部状态，不用被截断的显示数据。聚合率用对应分母，首轮明细与全轮均值明确标识。
