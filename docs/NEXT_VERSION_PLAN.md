# 下一版本实施计划：SimLab 0.3 多层维修

进度更新：用户选择“基地整件换 LRU、站内修 SRU”后，本计划的 0.3 子集已实施；具体交付与限制见 [V0.3.md](V0.3.md)。以下保留实施前计划，计划性维修仍未实现。

编写日期：2026-09-07。当前已发布代码基线：v0.2.0（302dee9）。本文为待实施计划，不表示功能已经实现；本次只上传代码与计划。

## 1. 当前进度

- 0.1：中文深蓝桌面、项目保存交换、一层 LRU 故障维修、两级保障、库存与组合资源排队。

下一步对应原路线图 M2。为控制范围，拆成 **0.3 多层纠正性维修** 与后续 **计划性维修**，不在一个版本同时引入层级维修、预防维修和老化。

## 2. 0.3 要解决的问题

当前 LRU 故障后，整个部件按一段修复时间处理。下一版需要表达：系统中的 LRU 因内部 SRU 故障而不可用，LRU 被拆下送修，维修站更换/修复 SRU，LRU 才能恢复服务。

目标是回答：故障来自哪个下层部件，LRU 维修为什么等待，增加某种 SRU 备件或某类维修资源对任务缺口有多大影响。

## 3. 版本范围

| 优先级 | 交付能力 | 边界 |
|---|---|---|
| 必须 | 系统 → LRU → SRU 的两层部件结构 | 先限制两层部件，不开放任意深度 |
| 必须 | 实物部件身份及父子安装关系 | 类型可复用，每件实物只能有一个物理位置/父件 |
| 必须 | 下层故障向上层不可用状态传播 | 串联关键部件；不加入冗余或降级运行 |
| 必须 | LRU/SRU 拆装、待件、修复与返库流程 | 保留已有两级保障网络，不同时扩展多级供应 |
| 必须 | 维修层级与等待原因结果 | 与 0.2 的任务缺口口径衔接 |
| 必须 | 旧模型兼容与验证用例 | 没有 SRU 的模型继续执行 0.2 规则 |

| 后续 | 定期检查、计划维修、老化 | 后续阶段单独定义和验收 |

## 4. 实现前冻结的语义

以下为建议实现规则，开发第一步须与原数据字典逐项核对。无法无损映射的语义不能伪装为原厂字段；需明确独立扩展格式和迁移方式。

1. **故障来源**：新增层级模型先采用叶子 SRU 故障驱动。具有 SRU 子件的 LRU 不同时叠加独立故障率；不支持的混合配置拒绝，避免重复计算故障。
2. **故障时钟**：仅设备实际运行时累计；已有故障或脱离运行系统的组件不累计运行故障。待命暂停，不能重复抽样重置未故障部件的剩余时钟。
3. **修复动作**：SRU 更换或修复后，上层 LRU 的所有必要位置均完整且可用时，才允许 LRU 修复完成。
4. **系统恢复**：需要可用 LRU 完成安装；父件返库不自动使原系统恢复，仍须遵守备件分配和拆装资源规则。
5. **资源申请**：沿用组合资源原子申请、站点 FIFO、班内开始及允许跨班完成。等待子件期间释放哪些资源必须按工序明确，不得隐式长期占用全部资源。
6. **运输与库存**：整件运输时子件随父件移动，不能同时在子件库再次计数；分离的 SRU 单独参与库存与运输。
7. **任务关联**：保持 0.2 的任务需求窗口、故障退出和即时补位。维修层级变化只通过设备状态影响任务供给。
8. **错误处理**：组成环、深度超限、重复实物安装、缺维修规则、不可满足资源组合必须在运行前或守恒检查中明确报错。

## 6. 实施顺序与检查点

- [ ] **A：字段与规则设计**。核对 SRU 类型、结构和维修字段；输出 docs/V0.3-SPEC.md 与最小输入模型。验收：每条规则有字段来源、执行语义及拒绝条件。
- [ ] **B：部件实例模型**。实现身份、安装、拆卸、搬运和位置统计。验收：环与重复安装被拒绝，装机/在库/在途/维修状态总数守恒。
- [ ] **C：层级故障与维修**。先使用确定性事件检验修复顺序，再接入随机故障。验收：父件和系统恢复时间符合手算。
- [ ] **D：任务与班次联调**。层级维修使用现有资源与日历，设备状态接入现有任务分配。验收：不重复分配设备，任务缺口与可用度分别积分。
- [ ] **E：界面与交换**。增加模型树、维修结果、示例、CSV、保存和项目包。验收：另一项目导入后可复现，历史 0.2 结果仍可查看。
- [ ] **F：发布验收**。执行全量测试、源码与打包版端到端检查、检查截图、生成 ZIP、记录验证证据，再提交并创建 v0.3.0 标签。

依赖顺序：A → B → C → D → E → F。界面布局可在模型契约确定后准备，但最终结果联调必须使用实际引擎。团队和可投入时间尚未明确，不承诺日历日期；估算后建议预留约 20% 的校准与回归余量。

## 7. 必须通过的基准案例

| 案例 | 预期结果 |
|---|---|
| 无故障两层结构 | 无停机，各级部件数量不变 |
| 固定第 5 小时发生叶子故障 | 只传播一次系统停机，不额外生成独立 LRU 故障 |
| 无备用 LRU/SRU，本地串行维修 | 例如系统拆卸 1h、LRU 内拆卸 1h、SRU 修复 4h、内部安装 1h、系统安装 1h，总停机 8h |
| 有备用 LRU | 系统可在完成 LRU 更换后恢复，旧 LRU 继续独立修复，不必等待其内部维修 |
| 有备用 SRU | 等件时间减少，故障 SRU 的修复与父 LRU 恢复可正确分离 |
| 两个系统争抢一个 SRU | 无重复领料；FIFO 与库存数量符合规则 |
| 父件运输时仍安装子件 | 子件不同时出现在仓库与运输件中 |
| 缺子件且等待补充 | 父件不可提前恢复；工序结束释放应释放的资源 |
| 拆装完成恰逢下班 | 后续工序按既有班次规则等下一次开班 |
| 相同型号多个安装位置 | 故障和维修只影响正确实物实例 |
| 相同模型、种子、引擎版本 | 运行结果可复现 |
| 不含 SRU 的旧模型 | 既有 0.2 测试及数值回归通过 |

随机结果比较应预先约定误差与重复次数，不用“曲线相似”作为正确性的依据。守恒检查按每种部件、每个实例和各物理位置执行。

## 9. 风险与预案

| 风险 | 应对与降级 |
|---|---|
| 原字段不能表达拟定规则 | 在 A 阶段决定映射或显式扩展；不在运行时猜测字段含义 |
| 任意深度维修引入循环与复杂状态 | 0.3 严格限制系统/LRU/SRU，更多层级后续单独扩展 |
| 健康子件被错误重置或重复计数 | 用实例身份、时钟保存和守恒断言约束每次转移 |
| 存储格式变更损伤历史项目 | 先测试迁移和备份；没有安全迁移方案就不发布格式升级 |
| 缺少真实案例 | 合成案例只验证实现；领域校准继续标记为未完成 |

建议角色：领域负责人确认维修规则；仿真开发负责实例与流程；桌面开发负责建模结果；测试负责独立基准与回归。人员未指定，角色可兼任，但期望值不能只从被测代码生成。
